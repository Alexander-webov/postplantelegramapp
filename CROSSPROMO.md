## Шаг 1. Применить миграцию БД

1. Открой [Supabase Dashboard](https://supabase.com/dashboard) → твой проект Постплана
2. Слева → **SQL Editor** → **New query**
3. Открой файл `supabase/migrations/011_crosspromo.sql` из проекта, скопируй **всё** содержимое
4. Вставь в редактор → нажми **Run** (или Ctrl+Enter)
5. Должно выполниться без ошибок. Миграция идемпотентна — если запустишь повторно, ничего не сломается

**Проверка:** слева → **Table Editor** → в списке таблиц должны появиться:
`cp_listings`, `cp_deals`, `cp_reputation`.

> Если выдаст ошибку `type "cp_topic" already exists` — это нормально при повторном запуске, миграция защищена от этого. Просто значит, что таблицы уже создавались.

## Шаг 3. Задеплоить Edge-функцию `cp-verify`

Это «проверяющий» воркер: он переводит сделки из «запланировано» в «опубликовано»,
а потом проверяет, что обе стороны честно опубликовали и не удалили рано.

1. Supabase Dashboard → **Edge Functions** → **Create a new function** (или **Deploy a new function**)
2. Имя: **`cp-verify`** (точно такое, без изменений)
3. Откроется редактор — **полностью замени** содержимое кодом из файла
   `supabase/functions/cp-verify/index.ts`
4. **Save** → **Deploy**

### Отключить проверку JWT (обязательно)

Cron будет дёргать функцию извне, поэтому JWT-проверку надо выключить:

1. Edge Functions → `cp-verify` → **Settings** (или **Details**)
2. Найди **Verify JWT** → переключи в **OFF**
3. Сохрани

> Если не выключить — cron получит 401 и проверка работать не будет.

## Шаг 4. Подключить cron к `cp-verify`

У тебя уже есть аккаунт на [cron-job.org](https://cron-job.org) (ты настраивал его для
`publish-scheduled-posts` и `delete-expired-posts`). Добавим третийджоб.

1. Войди на cron-job.org → **Cronjobs** → **Create cronjob**
2. **Title:** `postplan cp-verify`
3. **URL:**
   ```
   https://ВАШ_PROJECT.supabase.co/functions/v1/cp-verify
   ```
   (замени `ВАШ_PROJECT` на свой — тот же домен, что у других функций)
4. **Schedule:** каждые **15 минут** достаточно (проверка сделок не требует ежеминутности).
   Выбери **Every 15 minutes** или в expert-режиме: `*/15 * * * *`
5. **Advanced / Headers** — добавь заголовок авторизации (как у других джобов):
   - Key: `Authorization`
   - Value: `Bearer ВАШ_SERVICE_ROLE_KEY`

   Service role key берётся: Supabase → Project Settings → API → `service_role` (Reveal)
6. **Create**

### Проверка cron

1. На cron-job.org → джоб `postplan cp-verify` → **History**
2. После первого срабатывания статус должен быть **200 OK**
3. Тело ответа будет вида:
   ```json
   {"ok":true,"promoted":0,"completed":0,"failed":0,"recomputed":0,"ms":42}
   ```
   Нули — это нормально, пока нет активных сделок.

## Шаг 5. Проверить весь флоу руками (5 минут)

Лучший способ убедиться, что всё работает — пройти полный цикл самому. У тебя есть
2 канала, этого хватит.

1. Зайди на сайт → **Взаимопиар**
2. **Выставь первый канал**: выбери канал, тематику, сохрани → он появится в бирже
3. **Выставь второй канал** с **той же тематикой** (важно — иначе не сматчатся)
4. У первого канала жми **«Найти партнёров»** → в списке должен появиться второй канал
5. Жми **«Предложить ВП»** → впиши текст поста, выбери время публикации
   (поставь на **2-3 минуты вперёд** для теста), отправь
6. Перейди в **«Мои сделки»** → во «Входящих» будет предложение (т.к. оба канала твои)
7. Жми **«Принять»** → впиши текст второго поста → подтверди
8. Теперь оба поста **запланированы**. Через пару минут существующий планировщик
   (`publish-scheduled-posts`) их опубликует в обоих каналах
9. Проверь каналы в Telegram — посты должны выйти
10. Через `min_hold_hours` (по умолчанию 24ч, для теста можешь ставить 1ч)
    `cp-verify` проверит, что оба на месте, и переведёт сделку в **«Завершено ✅»**

> Для быстрого теста верификации поставь `min_hold_hours = 1` при создании сделки,
> и подожди час (или временно поправь логику). В обычной работе 24ч — норма.

## Как это работает (для понимания)

```
Админ A (биржа) ──предлагает──► Админ B
                                   │ принимает + пишет свой текст
                                   ▼
            Создаются 2 scheduled_posts:
            • пост A в канал A (про канал B)
            • пост B в канал B (про канал A)
                                   │
            Существующий планировщик публикует оба
                                   │
            cp-verify: scheduled → live (оба опубликованы)
                                   │
            Через min_hold_hours: проверка обеих сторон
            • оба на месте + охваты сняты → completed ✅
            • кто-то удалил рано → failed ❌ (нарушителю в репутацию)
                                   │
            Пересчёт cp_reputation → Verified-бейдж (≥5 успешных, 0 нарушений)
```

**Verified-бейдж** строится на реальных, непроворачиваемых данных — Постплан сам видит
посты и охваты через t.me. Это и есть преимущество над Telega.in, где статистику
можно накрутить.

## Если что-то не работает

**Пункт «Взаимопиар» не появился в меню** — сайт не пересобрался. Передеплой Railway,
проверь логи сборки.

**«Найти партнёров» не показывает никого** — у тебя только один канал в этой тематике,
или второй канал в другой тематике / вне диапазона охвата. Для теста выставь два канала
с одинаковой тематикой. Также проверь, что у канала-кандидата статус «Активен».

**Сделка застряла в «Запланировано» после времени публикации** — проверь, что основной
планировщик `publish-scheduled-posts` работает (его cron). ВП использует тот же
механизм публикации.

**Сделка не переходит в «Завершено»** — проверь, что `cp-verify` задеплоен, JWT выключен,
и cron его дёргает (History → 200 OK). Учти: проверка происходит только после
истечения `min_hold_hours`.

**Охваты в завершённой сделке пустые (`—`)** — каналы приватные (без @username).
Публичная страница t.me есть только у публичных каналов. Это ограничение Telegram.

## Что дальше (Фаза 2 — потом)

Когда наберётся ликвидность (хотя бы 20-30 активных каналов в одной тематике), поверх
этой же инфраструктуры включим **платный слой**: те же матчинг + проверка, но за деньги.
Каналы из биржи ВП станут твоим рекламным инвентарём. Платежи решим тогда (эскроу через
ЮKassa или директория без удержания денег). Сейчас это не нужно — взаимопиар бартерный,
денег не касается.
